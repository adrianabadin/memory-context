# PMC enrichment redesign: Symbol Cards (v3)

Date: 2026-10-09 · Status: proposal accepted for planning · Predecessor: `v2.md` (relational-query readiness audit)

## 1. Problem

Today's enrichment produces free-text explanations that an agent cannot use to answer "who calls X", "what does X depend on", or "which controller reaches X". The relevant code facts:

| Area | Current behavior | Evidence |
|---|---|---|
| Prompt inputs | Symbol code plus the file's `import` lines only. No callers, callees, file context, or project rules. | `cli/enrich-queue.mjs:192-203` |
| Output | Markdown prose (responsibility, inputs, output, immediate dependencies, role in module). Dependencies are guessed by the LLM, without IDs. | `src/memory-payload.mjs:6-38` |
| File symbols | Do not exist. | `src/extractors/tree-sitter/extract.mjs:154` |
| Class methods | Dropped for TS/JS/Python/Go/Rust/Java: `isTopLevel()` rejects non-root parents. Only C# keeps them. | `extract.mjs:32-53` |
| Architectural role | No taxonomy; only the free-text "role in module". | grep: none |
| `semanticSummary` | Dropped when the index is written. | `src/symbol-index.mjs:1-12` |
| `symbol_key` in agent-memory | Never passed on store/update, so it is 0/9,753 populated. | `cli/sync.mjs:93-118` |
| `graphNodeId` | Resolved by heuristic label matching; null for 91/468 main symbols. | `src/graph-node-resolver.mjs:22-63` |

## 2. Analysis of the initial approach

1. **Separate file symbols from code symbols.** Correct and necessary, but insufficient. Nodes need a typed hierarchy (`repo → package → file → symbol → member`), and non-code nodes (docs, data, config) must be kept out of code relations.
2. **Detect roles (service, repository, controller, view, model, interface).** High value. It must be **rule-based with evidence**, not decided by the LLM. The taxonomy depends on the stack: PMC itself has CLI commands, MCP tools, extractors, and stores, not controllers. The LLM is only a constrained tie-breaker.
3. **The LLM explains the function, its dependencies, and its dependents, linked by ID.** Right goal, wrong place for the data. Edges written into LLM prose go stale whenever any neighbor changes, and the LLM can invent IDs. **Edges must be computed from the graph at read time.** The LLM writes only the narrative: what the code does, why, its effects, and its contracts.

## 3. Target design: the Symbol Card

```
┌─ FACTS (deterministic, from graph.db, recomputed at read time) ─┐
│ id, kind, signature, location, callers, callees, imports,       │
│ importedBy, implements, tests, entrypoints, fanIn/fanOut, rank  │
├─ ROLE (rule engine + profile, with evidence and confidence) ────┤
│ role, layer, confidence, evidence[]                             │
├─ NARRATIVE (LLM, cached, keyed by input hash) ──────────────────┤
│ summary, behavior, sideEffects, errors, contracts, changeNotes  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.1 Principles

- **One identity.** `symbolKey` is the only ID across `graph.db`, `symbol-index.json`, cards, and agent-memory (`symbol_key`). Members extend it without breaking existing keys. This follows SCIP's stable symbol identifiers.
- **Facts are never generated by the LLM.** Any symbol the narrative mentions is validated against the graph.
- **Bottom-up narrative.** Symbols are enriched in reverse topological order of the call graph; strongly connected components are processed as one batch. Each prompt includes the one-line summaries of the symbol's callees and its top callers. This is the RepoAgent / HCGS approach; HCGS reports up to 82% relative improvement in top-1 retrieval precision on large repositories.
- **Input-hash invalidation.** `narrativeHash = h(code, signature, role, calleeSummaryHashes, promptVersion)`. A change in a symbol's callers updates its facts only. Regeneration propagates upward only when a callee's summary text actually changes.
- **Role-aware traversal.** Questions like "which controller reaches X" become traversals that stop at the first node with the target role.
- **Token budgets.** Cards render at `compact`, `extended`, or `deep`, ranked by relevance (PageRank, as in Aider's repo-map).

### 3.2 Role classifier

Signals, in descending weight:

1. Framework decorators or annotations: `@Controller`, `@RestController`, `@Injectable`, `[ApiController]`, `@Entity`.
2. Inheritance or implementation: `ControllerBase`, `models.Model`, `Repository<T>`.
3. Name suffixes: `*Controller`, `*Service`, `*Repository`, `*Dto`, `*View`, `*Store`.
4. Directory tokens: `controllers/`, `services/`, `repositories/`, `models/`, `views/`, `cli/`, `mcp/`.
5. Graph topology: controllers and entrypoints have high fan-out and low fan-in; utilities and models have high fan-in.
6. Side-effect markers: database clients, `fetch`/HTTP, `fs` writes, `process.argv`, `child_process`.

Output: `{ role, layer, confidence, evidence[] }` for each file and symbol. Profiles: `node-cli`, `express`, `nest`, `spring`, `aspnet`, `django`, `generic`, plus project overrides in `.planning/project-memory-context/roles.json`.

Default taxonomy: `entrypoint | controller | cli-command | mcp-tool | service | repository | model | dto | view | component | interface | adapter | config | util | test`.

The research basis is Dragan et al. (method and class stereotypes) and jMolecules/ArchUnit (stereotype metadata).

### 3.3 Narrative schema

Produced with Ollama's JSON-schema `format`, or by a subagent under the same schema, then validated:

```json
{
  "summary": "<= 25 words",
  "behavior": ["step"],
  "sideEffects": ["fs:write <path>", "spawn:<cmd>", "net:<host>", "db:<table>"],
  "errors": ["throws when ..."],
  "contracts": ["precondition / invariant"],
  "changeNotes": "what to check before modifying",
  "mentions": ["<symbolKey>"]
}
```

Validator rules:
- Every `mentions` entry must exist in the graph.
- The output must match the schema; on a mismatch, retry once, then mark `error`.
- Trivial symbols (getters, or fewer than 5 lines without branching) get a template narrative and make no LLM call.

### 3.4 Agent surface (MCP and CLI, both backed by `graph.db`)

| Tool | Answers |
|---|---|
| `pmc_relations(target, direction, relations?, depth?, stopAtRole?)` | Callers, callees, dependencies, dependents; "nearest controller" |
| `pmc_card(target, level?)` | Facts, role, and narrative for a symbol or file |
| `pmc_entrypoints_for(target)` | Which CLI commands, MCP tools, routes, or `main` functions reach X |
| `pmc_impact(target)` | Dependents, covering tests, affected roles |

`target` accepts a `symbolKey`, `path#name`, a graph node id, or a file path. Ambiguous matches return their candidates instead of empty results.

## 4. Phases

| Phase | Content | Exit criterion |
|---|---|---|
| F0 | Scope hygiene; `symbol_key`, `semanticSummary`, and `graphNodeId` fixes; golden-question harness | Golden relational questions answered correctly on the fixture; real-repo pollution 0% |
| F1 | Typed nodes, file cards, member extraction, facts, inbound callers, disambiguation; `pmc_relations` and facts-only `pmc_card` | The agent answers Q1–Q3 through MCP and CLI with symbol IDs |
| F2 | Role classifier and profiles | Role accuracy ≥ 90% on the fixture; evidence attached |
| F3 | Bottom-up structured narrative, validator, input-hash invalidation, concurrency | 0 invalid mentions; neighbor change does not re-run the LLM on dependents |
| F4 | `stopAtRole`, entrypoints, impact, token levels, Pi MCP registration | "Which controller reaches X" works from Pi |
| F5 | File and community rollups; eval metrics in CI | Eval report with relation accuracy, faithfulness, and task success |

## 5. Open decisions

- **D1. Edge source.** Keep graphify for edges and inject `symbolKey` through the resolver, or emit PMC's own tree-sitter call/import edges with native `symbolKey`. Decide at the end of F0 using the measured null and mismatch rate.
- **D2. Member key format.** Proposed: `lang|path|method|member|Container.name|arity`. Existing top-level keys stay unchanged.
- **D3. Execution environment.** The main checkout is dirty: 341 changes on `feat/community-naming-db-and-command`. The worktree-refresh incident guard (`assertCheckoutIdentity`) is still unmerged. Implementation must run in a branch or worktree where PMC refresh cannot reach the main memory DB. Land the guard first, or never run `refresh-context` or `sync` from the worktree.
