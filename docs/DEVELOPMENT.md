## Scope Exclusions and .graphifyignore

PMC walkers exclude non-source scopes and generator artifacts consistently:
- Walkers (`file-hash-store`, `structure-extractor`, `sanitize`, `bootstrap`, `file-watcher`) consult shared definitions from `src/walk-ignores.mjs`. Source walkers additionally preserve prior exclusions for `.opencode/**`.
- Scopes excluded: `.planning/**`, `.worktrees/**`, `graphify-out/**`, `.graphify_*.json`, build outputs (`dist`, `build`, `obj`, `bin`, `coverage`, `target`), vendor directories (`node_modules`), and version control metadata (`.git`).
- `.planning/**` declared intake artifacts remain explicitly readable via artifact paths under `.planning/project-memory-context/`.
- `ensureGraphifyIgnore(projectRoot)` in `src/graphify-runner.mjs` idempotently appends `.worktrees/`, `.planning/`, `node_modules/`, `graphify-out/`, and `.graphify_*.json` to `.graphifyignore` prior to invoking graphify, preserving existing user rules and comments. If writing `.graphifyignore` fails (such as on a directory collision), `runGraphifyUpdate` degrades gracefully without throwing.

## Symbol Index Semantic Summary Persistence

Enrichment pipelines persist a concise `semanticSummary` field in `symbol-index.json`. Queue workers and `pmc subagent-apply` record summaries via `persistEnrichmentSuccess` (`cli/enrich-queue.mjs`), while enrichment linking propagates entries via `applyEnrichmentResult` (`src/enrichment-linker.mjs`). For freeform enrichment text, `extractSemanticSummary` in `src/symbol-index.mjs` extracts the first sentence of the `Responsibility` section, bounded to a maximum of 200 characters. When updating existing entries, `upsertSymbolIndexEntry` preserves any pre-existing `semanticSummary` if the update omits the field. Query artifact loaders (`loadQueryArtifacts` in `src/query/load-artifacts.mjs`) fall back to graph node metadata (`node.metadata.semanticSummary`) whenever an index entry lacks a summary.

## Deterministic Graph Node Resolution

`attachGraphNodeIds({ symbols, graph })` first resolves an exact `metadata.symbolKey` (with legacy top-level `symbolKey` support only when metadata has no key). Conflicting nonempty metadata and top-level keys fail closed when either claims the requested key. Otherwise file/name fallback requires the same normalized relative `source_file`, exact name after removing Graphify's optional leading dot and trailing `()`, and consistent explicit kinds; a candidate with an explicit nonmatching key is excluded. If multiple candidates remain, it selects only a uniquely nearest valid `source_location` (`L<n>` or `L<n>-L<m>` with a positive end line not before the start) to the symbol's positive integer `range.startLine`; missing, malformed, invalid, or tied line evidence is ambiguous. A single exact file/name candidate can resolve without line data. It never uses `norm_label`, case folding, global-name matching, or array order. At the resolver level, unresolved symbols have `graphNodeId: null`, overriding any input value. The existing extraction pipeline can subsequently restore a prior ID via its `symbol.graphNodeId ?? prior.graphNodeId` merge; correcting that separate pipeline behavior is a follow-up outside this resolver/backfill change.

`resolverReport({ symbols, graph })` returns `{ total, resolved, unresolved, nullRate, reasons, symbols }`. `reasons` always includes `no-file-node`, `no-label-match`, and `ambiguous`; each returned symbol exposes an own, non-enumerable `resolutionReason` for diagnostics. It remains readable as `symbol.resolutionReason` but is excluded from object spread and JSON serialization, so it cannot leak into persisted worklist records. Aggregate counts/reasons remain enumerable and serialize normally. The empty input null rate is 0. This is fixture-level resolver diagnostic evidence, not an end-to-end resolver/pipeline accuracy score; a zero fixture null rate does not establish real-graph or Graphify pipeline accuracy.

## Typed Node Kinds in graph.db (classifyNodeKind, node_kind, traverse nodeKinds)

`src/graph-store/graph-db.mjs` persists a stable typed-taxonomy classification per node in the additive `nodes.node_kind` column, exported as the pure function `classifyNodeKind(node)` with taxonomy `NODE_KINDS = ['file', 'symbol', 'member', 'doc', 'config', 'data']` (plan Task 1.1). The legacy `kind` column (Graphify/extractor kinds such as `function`, `class`) and all existing `id`/`label`/`source_file`/`metadata` fields are preserved unchanged, so current readers (`graph-node-resolver`, query engine, renderers) keep their behaviour; consumers read the typed class from `node.node_kind` on `getNode`/`getNodesByFile`/`traverse` readback.

Classification is deterministic with this precedence: (1) structured member evidence — a member `kind` (`method`, `field`, …), a `symbolKey` whose kind segment is a member kind (generic 6-part keys index 2, C# 7-part keys index 4), or an explicit container field (`container`, `containerName`, …); (2) Graphify `file_type: 'document'` nodes → `doc`; (3) a path-shaped label (path separator, known code/doc/data extension, known config basename, or dotfile; graphify `.name()` call labels are explicitly not path-shaped) → `file` for code extensions, `doc` for markdown extensions, and `config` vs `data` for JSON/YAML/TOML-family files by basename rules (dotfiles, `package.json`/`docker-compose.yml`-style names, and any basename containing `config` are `config`; other JSON/YAML files, including lockfiles, are `data`); (4) structured symbol evidence — a `symbolKey`, a symbol `kind`, or `file_type: 'code'` plus `source_location` — but only when the label is not path-shaped, so file detection stays label/path-driven; (5) otherwise a conservative `data` fallback. Unknown, invalid, or label-only inputs never classify as code symbols. Limitation: until Task 1.2 member keys exist, Graphify method-shaped labels without container/kind evidence classify as `symbol`, not `member`.

Persistence is additive and migration-safe: `buildFromGraphJson` idempotently adds `node_kind` to pre-existing schemas via `PRAGMA table_info` introspection and a fixed (code-constant) `ALTER TABLE` statement, with every node/edge/meta write bound through prepared-statement parameters (no interpolated filters), and records `meta.schema_version`. `node_kind` is a reserved core field alongside `id`/`kind`: raw `graph.json` payload `node_kind` values are ignored on ingest (the computed classification is canonical), are never serialized into `metadata`, and only the persisted column value is reported by `getNode`, `getNodesByFile`, and `traverse`, so a contradictory or bogus payload key cannot shadow readback or filtering. `openGraphDb` rebuilds from `graph.json` when either `content_hash` differs (existing behaviour) or `schema_version` predates the current typed-kind layer, so legacy databases gain classifications on first open without dropping tables, reindexing, or losing `community_names` data. No new index is created; filtering happens in the traversal layer.

`traverse({ …, nodeKinds })` restricts results to the listed taxonomy values: omitting `nodeKinds` keeps the legacy unfiltered eligibility, node IDs, edges, depth, and default-filter behaviour unchanged for existing callers such as the query engine — the only readback difference is the additive `node_kind` field now present on every node object (payloads are not byte-identical to pre-1.1 node objects) — while an explicit list is a strict allowlist — including `nodeKinds: []`, which matches nothing. Seeds obey the same filter (a seed outside the filter yields an empty result), excluded intermediate nodes never appear in `nodes`/`edges`, never join the frontier, block path continuation, and consume no traversal depth, so `nodeKinds: ['file', 'symbol', 'member']` gives code-coherent paths. Duplicate valid entries collapse to the deduplicated set; any invalid, non-string, or injection-shaped entry (and non-array/null values) throws `TypeError` before any SQL runs, so a bad filter can never silently widen results. The filter is validated against the fixed `NODE_KINDS` allowlist and evaluated against the persisted column — never interpolated into SQL. The in-memory graph store (`in-memory-graph.mjs`) and `query-engine.traverseGraph` do not yet forward `nodeKinds`; wiring retrieval callers is follow-up work outside Task 1.1.

## Class Member Identity (D2 member keys, plan Task 1.2-A, member arity guard 1.2-B0, Python/Java adapters 1.2-B1, Go/Rust adapters 1.2-B2)

`src/extractors/tree-sitter/extract.mjs` extracts named top-level class methods for the JS/TS family (`javascript`, `typescript`, `tsx`; `.jsx` shares the javascript grammar). A method record is emitted only when its direct parent is the `class_body` of a top-level, named `class_declaration` that itself produced a top-level class symbol: object-literal methods, anonymous `export default class {}`, nested classes, abstract classes (no top-level class symbol yet), interfaces/type members, and computed/string method names fail closed and never acquire an invented container. Method records carry `kind: 'method'`, the **unqualified** `name` (`findById`), a structured `container` (`UserService`), the effective `exportScope: 'member'`, and `arity` counted by the member-specific declared-slot rule (unit 1.2-B0): every actually declared parameter in `formal_parameters` counts exactly one slot — optional, default, rest and destructuring parameters included — parameter names such as `self`/`cls` count normally, `comment` nodes inside the parameter list add no slots, and a TypeScript/TSX explicit `this: T` receiver parameter (real AST: a `required_parameter`/`optional_parameter` whose pattern child is the `this` keyword) is a compile-time receiver, not a runtime formal slot. That counter runs only on the JS/TS/TSX member path; top-level symbols and every other language keep the legacy `countArity` rule byte-for-byte — including its historical `self`/`cls` skip and comment counting — so historical global, C#, PHP and other-language key bytes never change.

Unit 1.2-B1 extends the same fail-closed container resolution to Python and Java enclosed types, using the same generic six-part D2 key. **Python:** a method record is emitted when the method (`function_definition`, or a `decorated_definition` wrapper containing it) is the direct child of the class body `block`, and that block belongs to an actual named top-level `class_definition` (module parent) which produced a class symbol in the pre-pass — the map is keyed by the class AST span, so a method never resolves a foreign same-named class. Nested classes, functions inside other bodies (including inside methods), and classes without a captured symbol (decorated top-level classes keep their existing capture behavior) fail closed; no container, property or anonymous symbol kind is invented, and `__init__` keeps its actual name under `kind: 'method'`. Python member arity is the **syntactic declared signature, never a runtime-call guarantee**: each declared parameter (identifier, default, typed, typed-default, `*args`/`**kwargs` — including typed variadics such as `*args: int`, distinguished by the actual AST child kind of the `typed_parameter`, never by parameter text or an identifier guess) counts one slot, `comment` nodes and the `*`/`/` separators add none, and unless the method carries the known syntactic bare `@staticmethod` decorator the first declared *positional* slot is excluded as the bound receiver **by position, not by parameter name** (renamed receivers are excluded; real arguments named `self`/`cls` after the receiver still count). Undecorated, `@classmethod` and unknown-decorator methods all follow Python's ordinary bound-method convention exactly as written — a syntactic ordinary convention only, with no runtime-call guarantee and no guessed decorator return types — dotted/called decorator forms are never treated as `@staticmethod`, and a first variadic (untyped or typed) counts one slot without ever being removed wholesale (a first-slot typed `*args: int`/`**kw: int` is a variadic shape, never receiver-elided). **Java:** `method_declaration` and `constructor_declaration` records resolve their container from the real grammar shapes — `class_body` → class, `interface_body` → interface, `enum_body_declarations` → `enum_body` → enum — for named top-level types with existing `@class`/`@interface` captures; constructors keep `kind: 'method'` and their actual AST name (e.g. `C.C`). Nested types, record bodies (no record container capture yet) and enum-constant bodies fail closed and are honestly unsupported in this unit. Java member arity counts each `formal_parameter` and varargs `spread_parameter` as one slot, ignores comment nodes, and excludes an actual AST `receiver_parameter` (explicit `Type this`) because it is a receiver, not an argument. Typed Java overloads with equal arity intentionally produce the **same canonical key** and are retained as distinct span records — that unresolved collision is documented for future 1.2b/1.2c collision handling; this unit neither de-duplicates such records nor invents a signature/ordinal extension. Legacy C#/PHP key branches remain untouched by these adapters.

Unit 1.2-B2 maps **Go** `method_declaration` records to the simple named receiver type: a value or a single pointer receiver, named or unnamed, resolves directly from the AST `receiver` field without requiring a same-file type declaration. Generic, scoped, complex and malformed receivers remain unsupported and fail closed rather than becoming global functions. The separate `parameters` field counts declared argument slots: grouped names such as `a, b int` count two; unnamed types and variadics count one; comments and the receiver add no slots. Ordinary Go globals retain their historical counter (including grouped-parameter undercount) and key bytes. **Rust** methods and associated functions directly inside a top-level `impl_item` resolve the simple named self type from its `type` field, **never the trait name** and without requiring a same-file struct/enum symbol. Each argument pattern counts one slot; `self_parameter` and a typed `parameter` whose actual `pattern` is `self` are excluded as receivers. Scoped/generic/complex self types, blanket type-parameter targets, nested impls, trait default methods and macro-generated methods are unsupported. Existing impl-as-class captures remain legacy records, not proof of a resolved parent. Same-arity methods from distinct trait implementations retain duplicate canonical keys as collision evidence; no trait/signature/ordinal suffix is invented. This is syntactic member extraction only, not type checking, parent binding, runtime dispatch or a live index/memory migration. C# keeps its seven-part keys and PHP its historical unqualified member keys; Kotlin/Swift adapters remain outside this bounded unit.

`buildSymbolKey` (`src/symbol-keys.mjs`) is pure and implements the D2 contract `lang|path|method|member|Container.name|arity`: when a `method` record carries a `container`, the key name slot canonicalizes to `Container.name` and the scope slot to `member`, e.g. `ts|src/services/user.service.ts|method|member|UserService.findById|1`. The builder never mutates its input and never rewrites the record's own `name`/`exportScope`; callers must always pass an unqualified name plus a separate `container` (there is no global name normalization). Every existing top-level key byte is unchanged, and methods **without** a container — including legacy C#/PHP output — keep their exact legacy key format (the dedicated C# 7-part branch is untouched). Fields/properties are not new symbol kinds, constructor/accessor/static/private methods are derived from real AST nodes under the same `method` kind, and collision/overload ambiguity is not resolved by invented ordinal identities. Member records dedupe by their actual AST declaration span, so same-line accessor pairs (`get value`/`set value`) and same-line overloads with different arities each keep their distinct D2 keys, while repeated captures of one node still collapse. Distinct same-line declarations that produce an identical canonical key are retained as separate records with that ambiguity intact (no ordinal/variant suffix, no array-order winner) so later native-relation work can detect the collision; this is an extractor limitation, not a resolved identity.

## Native Static File Imports (plan 1.2b-A)

`src/relations/native-imports.mjs` exports `extractNativeImports({files})`, where each caller-owned input is `{path, content}`. It returns `{files, relations, unresolved}` without reading project files or writing any graph, index or memory. Input paths are normalized project-relative paths; absolute/root-escaping paths, control characters and the key delimiter `|` reject with `TypeError` before parsing, without mutating input. A unique path gets the additive native endpoint `{id: 'file|<path>', kind: 'file', path}`; duplicate normalized paths get no endpoint and report `file-collision`. This convention does not rewrite legacy graph IDs or symbol keys. Symlinks, filesystem case equivalence and runtime module resolution are not inferred from source text.

The shipped JS/JSX/MJS/TS/TSX grammars parse static ESM import statements. A relative specifier resolves only to a **unique supported path in the supplied inventory**. Explicit supported extensions require that exact path; extensionless/other-suffix specifiers consider exact, supported-extension and `index` candidates without preferring one extension or directory. Missing files and multiple candidates remain unresolved. The caller supplies the analysis inventory; no filesystem scan, tsconfig/path alias, package lookup, `.js`-to-`.ts` remapping or dependency install is attempted.

Each resolved fact has `relation: 'imports'`, canonical file `source`/`target`, the raw `specifier`, line `range`, raw `bindings` (`imported`, `local`, `typeOnly`) and statement `typeOnly`. Named aliases, default imports, namespace imports and side-effect imports preserve syntax; type-only imports are structural file dependencies, **not runtime calls**. Binding names are not resolved symbol IDs or proof that an export exists. External/bare modules, dynamic imports, CommonJS calls, reexports, escaped specifiers, recognized `import_statement` nodes with parser errors, unsupported-language files and missing/ambiguous/colliding endpoints appear in `unresolved` with a `reason` and **no target**. Validity is checked per recognized statement, not for the whole source file; severely broken syntax collapsed into generic AST `ERROR` nodes may produce no record at all, but never a resolved import. Callers must never turn a raw specifier or binding into a graph edge. Calls, export/scope binding and collision-safe persistence are later units 1.2b-B/1.2c; this extractor is not wired into refresh or production graph generation and makes no semantic-accuracy or all-language coverage claim.

Focused checks: `node --test tests/native-imports.test.mjs` from `tools/project-memory-context`. Ordinary fixture verification must not execute `tests/relational-eval.test.mjs`, which can invoke Graphify; use an asserted explicit test-file array excluding that entire file.

## Native Static Declaration Calls (plan 1.2b-B)

`src/relations/native-calls.mjs` exports `extractNativeCalls({files})` over the same caller-owned `{path, content}` inventory as native imports. It returns `{files, symbols, relations, unresolved}`; symbol endpoints have `{id: symbolKey, symbolKey, kind, path}` and come **only from `extractSymbolsForFile`**, never from an arbitrary caller-provided key list. The collision registry checks both raw extracted key multiplicity and actual AST declaration multiplicity, including declarations hidden by historical same-line deduplication. Ambiguous keys are withheld; source attribution uses actual declaration ownership, not a nearest source line or name guess. Existing global/member descriptors and key bytes are not changed.

Resolved `calls` facts connect unique **static declarations**, not guaranteed runtime implementations or dependency-injection targets. Initial support includes direct top-level functions and arrow/function-expression variables; explicit local named/default exports and imported named/default/namespace aliases; concrete named classes with explicit constructors; direct `this` methods; static class methods; simple TypeScript typed class fields and constructor parameter properties; and local `const` receivers initialized with a direct `new` expression. `implements` does not invent inherited methods or prevent a concrete class's own methods from resolving. In contrast, classes with `extends` are conservatively unsupported. Implicit constructors get no invented method key. Call argument count never chooses between overloads or duplicate methods; class `method_signature`/abstract signature declarations remain ambiguity evidence alongside an implementation, and same-name ambiguity fails closed even when keys have different arities. Same-scope instance/static fields and constructor parameter properties shadow matching method names; computed fields conservatively withhold same-scope method targets.

Lexical guards are intentionally broad: parameters, destructuring, nested declarations and sibling-block bindings can all block a same-name global/import lookup. Reassignments, destructured writes, loop-assigned names and module-level hoisted `var` declarations block same-name lookup throughout the module. A named function expression's internal self-name is guarded as a local binding, not resolved to an unrelated module function. Local const-new receivers must be declared before the call in an enclosing block. Simple field annotations bind their declared class, not a runtime value; a class type parameter with the same name always withholds that annotation's target rather than resolving a global class: there is no full type checking, flow analysis, polymorphic dispatch, alias propagation, union/generic type resolution or inheritance traversal. Optional/computed/dynamic callees, unknown receivers, type-only value bindings, missing/non-exported/reexported targets and uncertain module paths remain unresolved. Presence of a `with` statement or a syntactic direct `eval` call conservatively disables call binding for that module (even if a runtime analysis could establish that the `eval` name was shadowed). Modules with parser errors are also withheld from positive call facts.

Nested closures and top-level expression calls have no invented outer source symbol. Unresolved diagnostics carry `relation: 'calls'`, source context, raw `callee`, line `range` and `reason`, with **no target**. Resolved facts additionally carry a canonical `target` present in `symbols`; only these resolved facts can become graph edges. The layered-app fixture proves the static `main` → `UserController.getUser` → `UserService.findById` → `UserRepository.findOne` chain and the `formatName` call; this is structural fixture evidence, not a semantic-accuracy score. Canonical file/source validation inherits the import slice; neither extractor is wired into production refresh, graph persistence or live memory migration yet (plan 1.2c).

`src/graph-store/native-relations.mjs` persists those resolved facts into the additive `native_edges` SQLite table (`persistNativeRelations(db, extractResult)`; also exposed on the `GraphStore` facade from `openGraphDb` as `persistNativeRelations`/`listNativeEdges`/`getNativeEdgesFor`). The table is deliberately outside the Graphify-managed `nodes`/`edges` pair, so a `graph.json` rebuild never wipes native edges and native persistence never disturbs legacy tables, communities, `node_kind` or the resolver/backfill paths. Persistence is two-phase and fail-closed: every fact is validated before any row is written, so a batch containing a raw string target, an unknown relation, a file endpoint without the `file|` prefix or a `symbolKey`/`id` mismatch throws `TypeError` and writes nothing. Unresolved facts are never edges — they are counted per relation in the returned summary. Re-persisting the same `(source, target, relation)` triple is idempotent (unique index, counted as duplicate). Readback returns canonical endpoint pairs `{source: {id, kind}, target: {id, kind}, relation}` in deterministic order, which is the seam the Task 1.3 facts builder consumes without re-resolving endpoints.

`src/cards/facts.mjs` exports the read-only `buildFacts(graphDb, symbolKey, {depth})` returning `{id, kind, signature, location, callers, callees, imports, importedBy, implements, tests, fanIn, fanOut}`. Named calls use depth-bounded native edges; constructor instantiations remain persisted but excluded. Symbol imports consume exact resolved binding endpoints from `listNativeImportBindings`, never all exports of an imported file: layered-app q11 now matches exactly `User` and `UserService`. Missing legacy bindings yield no guessed symbol imports. File imports and file-scoped `importedBy`/`tests` retain their existing conventions. Relation lists are sorted; `implements` remains empty without evidence; unavailable signature/line metadata remains null. Facts never write the store. Focused check: `node --test tests/card-facts.test.mjs`.

`src/relations/native-import-bindings.mjs` adds `extractNativeImportBindings({files})` without changing the established file-import API. It resolves explicit local named/default exports (including aliases and type-only declarations) to unique canonical extracted keys using AST declaration spans. Namespace imports, missing exports, reexports, collisions and ambiguous evidence have no symbol target. Persistence keeps syntax metadata and optional resolved targets in the rebuild-safe companion `native_import_bindings` table; all bindings validate before writes, and a savepoint rolls back the entire batch on SQL errors. Evidence accumulates idempotently for a caller-owned immutable snapshot; it is not a live refresh/replacement API. Conflicting evidence is retained but withheld from resolution, rather than choosing a last writer. Focused check: `node --test tests/native-import-bindings.test.mjs`.

`src/cards/file-card.mjs` exports the read-only `buildFileCard(graphDb, filePath)` returning `{path, kind: 'file', exports, importsFrom, importedBy, symbolCount, members}`. Symbol entries link their registry `id` and canonical `symbolKey`; file dependencies link `file|<path>` endpoints. Exports/members/counts include only uniquely identified registry symbols from the requested file; ambiguous keys are withheld, not overwritten. Native file imports remain file-scoped. Paths normalize separators and reject absolute/root-escaping/control-character inputs. Unknown files return empty cards, and all reads leave persisted rows unchanged. Focused check: `node --test tests/file-card.test.mjs`.

Focused checks: `node --test tests/native-calls.test.mjs tests/native-calls-blockers.test.mjs tests/native-imports.test.mjs` from `tools/project-memory-context`; keep the entire `relational-eval.test.mjs` excluded from ordinary verification as above.

## Role Classifier and Profiles (plan F2 2.1–2.3, R1 bounded to generic + node-cli)

`src/roles/classify.mjs` exposes `loadProfile(name)`, `classifySymbol(record, {profile, allSymbols})` and `classifyFile({path}, {profile})`. Each returns exactly `{role, layer, confidence, evidence[]}` for a file or symbol. `confidence` is a finite 0..1 heuristic evidence strength (noisy-OR over the agreeing signals' weights), not a calibrated probability or semantic-accuracy score. With no supporting evidence the classifier returns the documented unknown shape `{role: null, layer: null, confidence: 0, evidence: []}` — it never invents an "unknown" role enum. A member inherits a **uniquely** identified container's role (same file, one matching class); an ambiguous or absent container fails closed rather than resolving by array order, and a member's own stronger provided evidence (a structured decorator annotation) overrides the inherited role. Classification is pure: it reads no project, fixture, or graph at call time, never mutates its inputs, is deterministic, and never hardcodes golden keys or paths.

Signals (`src/roles/signals.mjs`) cover the six S1 evidence kinds, descending by the accepted v3 §3.2 priority. Decorator and inheritance evidence each have a strong structured form (caller-provided from real syntax inspection) and a weaker marker form:
For members with unique container evidence, a structured annotation whose individual weight exceeds the container-role weight selects its annotated role before pooling agreeing evidence. Weak suffix/path signals cannot outvote that explicit override. An absent or weaker annotation keeps the ordinary weighted scoring behavior.

| Kind | Signal | Source | Honesty label |
|---|---|---|---|
| decorators | `framework-annotation` (0.9) | caller-provided `annotations.decorators` | structured syntax evidence (trusted, not re-verified) |
| decorators | `decorator-factory` (0.6) | local function named like a decorator | name marker, decorator syntax **not verified** |
| inheritance | `structured-heritage` (0.85) | caller-provided `heritage` clauses (dotted/generic/compound-base forms) | structured syntax evidence |
| inheritance | `container-role` (0.75) | unique same-file container | member inheritance |
| suffix | `name-suffix` (0.6) | name ends with a stereotype (`*Service`) | name/path marker, never a verified fact |
| directory | `directory-token` (0.5) | deepest matching path segment (`services/`) | path marker |
| topology | `topology` (0.35) | caller-provided fan-in/fan-out | weak heuristic |
| side-effects | `side-effect-marker` (0.3) | caller-provided markers (`child-process`) | marker, **not** a verified execution fact |

Name-suffix stereotypes are gated off for abstraction kinds (`interface`/`type`) and inside test scopes (a directory token mapped to the `test` role): those symbols take their role from directory/kind, not a coincidental suffix. Both gates are profile-driven, not hardcoded.

Structured heritage clauses are normalized to a base type name that recognizes the accepted v3 inheritance **forms** — dotted (`models.Model`), generic (`Repository<User>`), and compound-base (`ControllerBase`) — rather than matching the raw clause end-wise. The base name is matched against the declarative `heritageTypeRoles` table (compound base classes like `ControllerBase`/`RepositoryBase`/`ServiceBase`) and then the stereotype table (exact or suffix). This is conservative, profile-driven mapping, not a new-language extractor and never invented AST from comments or names.

`loadProfile` returns a **deep-isolated** profile: `generic` is a `structuredClone` and `node-cli` is merged from clones of both profiles, so the returned tables share no object identity with the module-owned JSON. Mutating or deep-freezing a returned profile can never corrupt a later `loadProfile` result, and classification stays pure.

The public resolved-profile API fails closed **before scoring** (B3): every weight in `profile.weights` must be a finite number in `[0,1]` (bad values throw `TypeError`, never silently clamped) and every role a mapping table can produce must be a declared key of `profile.roleLayers`. Legitimate declared extensions — a role added to `roleLayers` and used in a table — pass; an undeclared role or out-of-range weight throws instead of being invented. A second gate then enforces the same contract on the **actually generated signals**, after collection but before the noisy-OR arithmetic and before any return: a required-but-missing active weight (which would otherwise yield a non-finite confidence) and an implicit/hardcoded role no table declares (such as the decorator-factory role) both throw `TypeError`. This signal-level check is generic over whatever fires — no hardcoded special case and no silent clamp.

Profiles are declarative JSON in `src/roles/profiles/`. `generic` is stack-agnostic; `node-cli` overrides its `cli/` token with `cli-command` and adds PMC conventions. Packaged `express`, `nest`, `spring`, `aspnet`, and `django` profiles extend generic with configured annotation names, base types, paths, or caller-provided side-effect markers. They do not scan dependencies, extract additional syntax, or verify runtime effects.

`loadProjectProfile(projectRoot, { profileName: 'generic' })` in `src/roles/profile-loader.mjs` reads only `.planning/project-memory-context/roles.json`. Missing files return the caller-selected packaged profile without creating anything. An explicit `extends` selects a packaged base; project mappings then override matching keys. No automatic stack detection or global configuration lookup occurs.

```json
{
  "extends": "nest",
  "roleLayers": { "handler": "application" },
  "directoryRoles": [{ "token": "handlers", "role": "handler" }],
```

## Bounded Narrative Execution Pool (F3.6 / S12, N6A)

`src/cards/batch-pool.mjs` exports the pure `runNarrativePool({symbolKeys, edges, concurrency, run, prepareBatch?})`. It plans with the unchanged F3.2 `orderNarratives` batches, then executes those SCCs through a bounded worker pool: at most `min(concurrency, number of keys)` workers run at any moment, and preparation plus run callbacks together share that ONE global bound — both are queued as work items on the same FIFO queue and executed only inside worker slots, so preparation can never open a second, hidden pool beside `run` (there is no such thing as "concurrency preparation slots plus concurrency run slots"). Unrelated SCC members occupy shared slots simultaneously while a caller SCC never dispatches any member until ALL members of every callee SCC have SETTLED — settled means fulfilled or rejected, not validated or successful; deciding what a failed callee means for its caller belongs to the pipeline unit (N6B), and no successor value is ever fabricated from a failure. Each SCC follows an explicit guarded lifecycle `waiting -> queued -> preparing -> prepared -> completed` (`preparing`/`prepared` are skipped without a `prepareBatch`), so a batch is opened, prepared and dispatched exactly once — including synchronous preparation-failure chains. Cycles and self-calls are intra-SCC and therefore never become waits (no self-deadlock), each SCC passes through the planner exactly once with no fixed-point loop, and readiness releases only push queue items (iterative), so failure chains of arbitrary depth — e.g. a 3000-symbol chain of synchronous preparation failures — never recurse and still settle every member with the exact original error.

`run(symbolKey)` may return a value or a promise; a rejection or a synchronous throw becomes that key's rejected settled result while independent jobs keep running, and every already-launched job — preparation or run — is awaited inside a worker before the pool resolves. The optional `prepareBatch(memberKeys)` runs exactly ONCE per SCC with a fresh copy of the sorted member array, occupies a bounded slot for its whole execution, and is awaited before any member dispatch; its rejection (or throw) settles every member of that SCC as rejected with the original error, releases the caller SCCs only after all members have settled, and never invokes `run` for them — so none can report members as fulfilled.

The resolved value is an array of `{key, status: 'fulfilled', value}` / `{key, status: 'rejected', reason}` entries (the `Promise.allSettled` shapes plus `key`) ordered by the N2 canonical flattened SCC/member order — never completion order — so two runs over the same graph return identical ordering. Validation happens fully before any callback: `concurrency` must be a positive finite integer, unknown options are rejected (never ignored), `run`/`prepareBatch` shapes are checked, and duplicate keys or malformed/non-canonical endpoints reject through `orderNarratives` with no partial execution. An empty graph resolves `[]` without invoking callbacks. Caller `symbolKeys`, `edges` and callback values are never mutated; the module uses no timers, I/O, providers or state.

This unit is pure scheduling only: it does not read `PMC_CONCURRENCY` (honoring it inside the Ollama loop plus the `worklist.json` file-lock retry is N6B), opens no graph database, keeps legacy text mode as the default and activates nothing. ## Queue Concurrency, Fresh SCC Contexts and Serialized Writes (F3.6 / S12, N6B)

`cli/enrich-queue.mjs` now runs its actual loop through the N6A `runNarrativePool` helper: the selected symbols are dispatched with `concurrency` = the effective `PMC_CONCURRENCY` bound (the historical module constant — raw default 8, non-positive fallback 1 — read once at import, unchanged `parseQueueConcurrency` semantics), and a programmatic-only `main({concurrency})` override exists for tests; a supplied non-integer or sub-1 value rejects with `TypeError` BEFORE the first file write (zero provider calls, untouched worklist), and there is no CLI flag, config key or default narrative activation. Real model and tokenizer jobs are bounded: each symbol's prompt build, Ollama tokenizer probe, provider/fallback driver invocation and subagent-route write occupy ONE pool worker slot, so at most `min(concurrency, pending)` jobs are in flight, independent jobs overlap, preparation and run share the single global N6A bound, and an empty selection still finishes with zero provider calls. Every launched job is awaited before the run report: results, errors and subagent-queued records are collected per symbol key during execution and aggregated afterwards in the ORIGINAL selected worklist order (pending first, stale last), so the final JSON keyset, `timing` array order, per-symbol request bytes and summary counts stay identical to the sequential baseline regardless of completion order; only wall-clock message ordering changes with concurrency. Progress messages stay in their historical formats with two honesty updates: the start line reports what actually runs — `Starting concurrent enrichment` when the effective bound is above 1, the exact historical `Starting sequential enrichment` at 1 — and the token-routing metrics line shows the configured concurrency instead of the hardcoded `1 (sequential)`.

Structured dependency plan: with an explicit `narrativeResolver` and at least two selected symbols, the queue builds canonical N2 `calls` edges (`{relation:'calls', source:{id}, target:{id}}`) from the COMPLETE authoritative callee keys — the stored accepted `calleeSummaryHashes` maps AND the resolver's callee list, never the top-5 display callers — while a graph of fewer than two selected symbols cannot contain an in-graph edge and therefore triggers no discovery resolution. Dispatch order: narrative mode keeps the pool's canonical graph order (SCC barrier and canonical member order), while the legacy flow — no resolver, no edges — dispatches in the SELECTED WORKLIST ORDER at any concurrency through a stable zero-padded ordinal key mapping, so a concurrency-1 legacy run reproduces the baseline request/DONE sequence exactly and concurrent legacy runs still fill the bound (FIFO) instead of silently running sequential. Discovery may resolve context purely to shape the graph; the context that feeds the cache and the prompt is ALWAYS resolved fresh inside `prepareBatch` at SCC ready — after every dependency batch settled (fulfilled or rejected) — snapshotted immediately (N5 B1 ownership), then overlaid with the same-run accepted FULL summaries of finished dependencies copied from a map that only validated acceptances and validated cache reuses ever populate (a failed job never fabricates a "fresh" summary). This is what keeps a static resolver from feeding a stale prompt or fingerprint: a diamond caller's prompt carries the same-run callee summaries, editing a caller never re-runs the callee, a byte-identical callee summary never re-runs the caller, and cycles resolve exactly once per member at the barrier — one pass over the prior accepted summaries, no fixed-point loop and no claim of perfect cycle convergence. A `prepareBatch` rejection settles every member of that SCC as an honest per-key `error` (persisted worklist status, counted in the summary) even when `run` was never invoked, while its caller SCCs still run — failure is settlement, never validation — and the resolver is never called after a prompt exists (C1 race guard).

Shared-state safety: `src/cards/queue-state-io.mjs` provides ONE in-process coordinator per canonical enrichment directory (canonical file-system path: `resolve()` on every platform, plus realpath and case folding on win32 so case/junction aliases of one physical directory share one scope while case-sensitive platforms keep distinct scopes), shared by the direct runner's saves, `persistEnrichmentSuccess`'s complete multi-file acceptance (memory artifact + worklist merge + index merge + upward propagation + sync-manifest append as ONE scoped transaction), the queue-state/queue-appends writes and `pmc subagent-apply`'s mutations. The coordinator is reentrant (a transaction's nested locked helpers run inline under the same hold — one mutex covers the whole transaction, never half of it) and drains its registry after idle, so no scope keys leak across runs. Model generation never runs under the coordinator — only file operations — so serialization costs no throughput, and the scope is explicitly in-process: no persistent lock file and no interprocess locking promise are added. Every queue JSON write is atomic (own `<path>.<pid>.tmp` + rename, cleaned up on failure) and every file operation is wrapped in a bounded exponential retry for the transient Windows lock codes `EBUSY`/`EPERM` ONLY (15/30/60ms, four attempts, then the original error surfaces); `EIO`, `EACCES` and validation errors fail on the first attempt, an exhausted retry leaves the previous target bytes untouched so no false `DONE`/accepted state can appear, a locked read that survives the retry fails the save visibly instead of merging from an empty disk (which could revert accepted fields or explicit `EXPLICIT_STALE_REASONS` marks), and inference is NEVER retried to repair a file lock. Acceptance publication is staged (B4): `persistEnrichmentSuccess` snapshots the prior worklist entry and index record, writes the accepted memory artifact, then the index acceptance, and the COUNTED worklist acceptance LAST — any write failure restores the exact pre-acceptance shared state and rethrows, so a rejected acceptance never survives in memory and never lands on the worklist surface where the disk-enriched merge could resurrect it; the final report then counts that run as the honest `error` it is (never `enriched`/`complete` success for uncommitted acceptance), even when the follow-up error save itself fails, because the counts derive from the in-memory worklist. A partial multi-file write stays fail-closed as an accepted cache: the cross-artifact evidence checks require the worklist, index and artifact fingerprints to agree, so no remaining partial state can produce a cache hit. Upward invalidation marks are published only after the acceptance is durable (a failed mark write is reported with its exact message and retried by the next save/checkpoint), and the historical "disk enriched wins" merge semantics plus every accepted-status rule are unchanged.
