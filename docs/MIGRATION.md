# Migration Guide: Unified PMC MCP Server

> **Status**: The unified `pmc` MCP server is **planned but not yet implemented**. This guide describes the target state from the `unified-pmc-mcp-background-actions` proposal. Currently, PMC uses two separate MCP servers: `pmc-query-server` (query tools) and `pmc-agent-memory` (memory tools).
>
> The composable foundation (`query-tools.mjs` with `registerQueryTools()`) already exists in `tools/project-memory-context/mcp/` and is ready to be composed into the unified server when implementation begins.

This guide explains how consuming projects will migrate to the unified `pmc` MCP server when it becomes available.

## What changed

Previously PMC injected **two** separate MCP servers into your agent config:

| Old server key       | Old tool prefix          | Example old tool name              |
|----------------------|--------------------------|------------------------------------|
| `pmc-query`          | `pmc-query_`             | `pmc-query_pmc_get_context`        |
| `pmc-agent-memory`   | `pmc-agent-memory_`      | `pmc-agent-memory_store`           |

**Planned**: PMC will ship a single **unified `pmc` server** (`pmc-mcp-server`) that composes both the query tools and the memory tools into one process under one namespace.

| New server key | New tool prefix | Example new tool name |
|----------------|-----------------|------------------------|
| `pmc`          | `pmc_`          | `pmc_get_context`, `pmc_store`, `pmc_search` |

## Why

- One process instead of two (lower Node overhead, shared lifecycle).
- One tool namespace (`pmc_*`) that matches the mental model of "PMC tools".
- The unified server defers the embedding-model download until the first real `store`/`search` call (lazy embedder), so `tools/list` answers instantly.

## What you need to do

### Generated configs (recommended path)

When the unified server ships, if your project's MCP config is generated by PMC (`plugin-config.mjs` / `setup-bootstrap.mjs`), **nothing manual will be required**. Regenerating config will emit `pmc` as the primary server. The old `pmc-query` and `pmc-agent-memory` server keys will remain as **transitional aliases for one release**, so any hardcoded or unmigrated callers keep working during the transition.

### Hand-written references

When the unified server ships, if you have hand-written references to the **old prefixed tool names**, update them to the unified `pmc_` namespace:

| Old                                | New                  |
|------------------------------------|----------------------|
| `pmc-query_pmc_get_context`        | `pmc_get_context`    |
| `pmc-query_pmc_search_symbols`     | `pmc_search_symbols` |
| `pmc-agent-memory_store`           | `pmc_store`          |
| `pmc-agent-memory_search`          | `pmc_search`         |
| `pmc-agent-memory_recall`          | `pmc_recall`         |

A grep-based audit (`npm run audit-stale-tool-refs` in `tools/project-memory-context`) fails CI if any non-allowlisted `pmc-agent-memory_` / `pmc-query_` prefixed reference remains. See `.config/opencode/audit-allowlist.txt` for the documented transition exceptions.

## Transition window (when the unified server ships)

- **Ship release**: the unified `pmc` server will be primary; `pmc-query` and `pmc-agent-memory` will remain callable through compatibility aliases.
- **Next release**: the legacy aliases are scheduled for removal. Migrate any remaining hardcoded references before then.

## New session-ledger controls (planned)

The unified server will also expose explicit session-ledger lifecycle tools:

- `forget_session_item(id)` — **soft** delete: sets `status='forgotten'` so the record is hidden from default retrieval/search but remains recoverable.
- `purge_session_item(id)` — **hard**, destructive delete: removes the row and its embedding permanently. Never triggered automatically by decay/retention.

Soft forget is the safe default. Hard purge is irreversible and intended for privacy/cleanup only.
